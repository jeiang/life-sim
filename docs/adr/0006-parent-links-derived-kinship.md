# Family is stored as parent links; kinship is derived

Every person, the player included, can store their parents: the Core-owned person state container `_parents` (`Person.state._parents`, `{ "<parent id>": <kind code> }`, kind `birth` 1, `adopted` 2, `step` 3). Nothing else about the family is stored. What one person is to another (grandparent, half-sibling, cousin, in-law) is computed from those links by the Core (`kinshipOf(world, viewer, other)`), relative to a viewer: the subject of the expression, which is the player pointer. We rejected hand-set family roles as the source of names because they cannot say who a grandparent is, break when the player pointer moves to an heir, and need a relabel table at succession. Relationship role rows stay for closeness and for non-family roles (friend, partner, coworker); they no longer name family.

The links sit in a reserved per-person state container (the `_milestones` and `_schedule` pattern, [state containers](../spec/pack-format/state.md)), not in a new `Person` field, so the save codec, canonical serializer and world hash need no change and the save schema stays 6: a person with no recorded parent has no entry.

## Consequences

- Kinship ids are Core-owned and gender-neutral: `parent`, `grandparent`, `great-grandparent`, `child`, `grandchild`, `great-grandchild`, `sibling`, `half-sibling`, `step-sibling`, `adopted-sibling`, `aunt-uncle`, `great-aunt-uncle`, `cousin`, `niece-nephew`, `step-parent`, `step-child`, `spouse`, `parent-in-law`, `sibling-in-law`, `child-in-law`. Packs reference them as bare ids (no `/`) in `is_kin` and `count_kin`. A new id is a Core release (ADR 0002). Labels (`mother`, `uncle`, ...) are Core text (`kinshipLabel(id, gender)`), chosen by the person's gender when it is male or female, neutral otherwise.
- Derivation: ancestors by birth or adoption up to three generations; the closest common ancestor (fewest generations in total, then nearest the viewer, then lowest id) gives the relation by its distances (`0,n` descendant, `n,0` ancestor, `1,1` sibling, `2,1`/`3,1` aunt or great-aunt, `1,2` niece or nephew, `2,2` cousin). Anything farther (great-nieces, second cousins, great-great-grandparents) has no kinship id. Sibling kind: they share a parent by birth or adoption; `adopted-sibling` if any shared link is adoption, else `sibling` when both have exactly the same parents, else `half-sibling`. Step links are followed one hop only: `step-parent`, `step-child`, and `step-sibling` (two people who share a parent through a step link). A step-parent's relatives are not kin.
- In-laws come last: `spouse` (both ends of a `spouse` role row), `parent-in-law` and `sibling-in-law` through the spouse, `sibling-in-law` also for a sibling's spouse, `child-in-law` for a child's spouse.
- Succession needs no relabel map: moving `playerId` to the heir re-derives every name from the heir's position (`kinshipOf(world, heir, other)`).
- Role writes keep the tree in step: `spawn_person(role, ...)` and `relationship(p).role = role` with a role whose last id segment is `parent`, `sibling`, `child` or `grandparent` add the matching link (a sibling takes the person's parents with their kinds; a child gets the person and the person's spouses as birth parents; a grandparent becomes a birth parent of the person's first birth or adopted parent; with no parent to attach to, nothing is added). New lives link the generated parents and siblings the same way, so they add no people. Adoption and step links have no effect that creates them yet; later content adds them through `addParentLink(world, child, parent, kind)`.
- API for later consumers (storylet targets, text placeholders, UI, succession, guardian choice): `kinshipOf`, `kinOf(world, viewer, { alive? })` (everyone with a kinship id, in person id order), `countKin`, `kinshipLabel`, `parentLinks`, `addParentLink`, `linkFamilyRole`.
- Expressions: `kin(person)`, `is_kin(person, id)`, `count_kin(id, min_age, max_age)` (living people), relative to the subject. `person` names the scoped person or one bound by `spawn_person(...) as <name>`; the kinship id is a bare word or a string and is checked at build time.
- Storylets and text (#218): `target` on a `scope: person` storylet accepts kinship ids as bare words beside role ids (a compiled role id always holds a `/`, a kinship id never does; the person fits when any entry matches `kinshipOf(world, player, person)`, and a same-Pack role with the same bare id keeps meaning the role). `{person.kin}` / `{<name>.kin}` print the gendered label (`kinshipLabel`), empty for no kin. The web profile and the relationships list show the label in place of the role label when there is one. The harness raises fault `unresolved-family` when a person with a family role has no kinship id.
